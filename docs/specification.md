# المحاسب الذكي
## مخطط المنتج والمعمارية والمواصفات المحاسبية والأمنية

**تاريخ البحث:** 29 أكتوبر 2026  
**الحالة:** وثيقة تصميم أولية للنقاش والاعتماد؛ ليست نظامًا منفذًا أو شهادة امتثال.  
**التوجه:** Rust + Askama، عربي أولًا، محلي/سحابي/هجين، موجه للسوق اليمني وقابل للتوسع.  
**مرجعية تجربة الاستخدام:** الصور الثلاث المرفقة من صاحب المشروع، خاصة بطاقات الإدارات المجسمة والمساعد الجانبي.

---

## 1. ملخص تنفيذي

«المحاسب الذكي» نظام مالي وإداري قابل للتكوين يخدم المنشأة ذات الفرع الواحد والشركات متعددة الفروع. الواجهة الرئيسية قائمة على بطاقات الإدارات؛ كل بطاقة تفتح أقسام الإدارة وشاشاتها بحسب صلاحيات المستخدم. المساعد يفهم الطلبات المقروءة والمسموعة، ويقترح إجراءات ويملأ مسودات قابلة للتعديل؛ ولا يرحّل عملية مالية دون اعتماد صريح من مستخدم مخول.

**قرار معماري مبدئي:** نواة Rust واحدة معيارية (modular monolith)، واجهة HTML بقوالب Askama، وخادم ويب خفيف بـ Rust. يُستخدم JavaScript محدود ومراجع للأجزاء التي تحتاج تفاعلًا حيًا؛ Askama ليس بديلًا كاملًا عن منطق المتصفح. PostgreSQL هو قاعدة المرجع لبيئات الخادم متعدد المستخدمين. يعمل الفرع أثناء الانقطاع في وضع محلي مضبوط، ثم يتزامن عبر بروتوكول أوامر قابل للتدقيق بدل دمج قواعد البيانات تلقائيًا.

**ضبط مهم:** دعم القيد الثلاثي المقصود متاح عبر طبقة إيصالات مشتركة موقّعة وسجل موزع مرخّص اختياري متعدد الأطراف؛ القيد المزدوج يظل أساس الدفتر المالي لكل منشأة. لا يُعلن تحقيق القيد الثلاثي لمعاملة لا تمتلك الإيصال المشترك والتحقق المتفق عليه.

**ليس وعدًا بالجاهزية:** يجب تنفيذ الاختبارات ومراجعات الأمان والمحاسبة والقانون والقبول التشغيلي قبل استخدام النظام ببيانات أو أموال حقيقية. اختيار تقنية أو منتج مفتوح المصدر لا يعني أنه قد تم اختباره أو دمجه بالفعل.

## 2. ما طلبه صاحب المشروع وما يترتب عليه

| المتطلب | استجابة التصميم | القيد أو المخاطرة |
|---|---|---|
| اختيار المنطقة والنشاط والمنشأة والفروع | إعدادات مؤرخة ومقسمة بحسب الشركة والفرع والصلاحيات | القواعد القانونية والضريبية لا تُفترض ثابتة لكل اليمن |
| اختيار العملات وتعدد أسعار الصرف | عملة وظيفية وعملة عرض وعملة مستند وأسعار حسب السوق والتاريخ والمصدر | تغيير العملة الوظيفية ليس زر تحويل أرصدة تاريخية |
| اسم مستخدم عربي وكلمة سر بلا اشتراط نوع؛ حتى حرف واحد | Unicode للأسماء وكلمات السر؛ يختار المستخدم كلمة من حرف أو رقم واحد أو أكثر دون فرض نوع المحارف | حرف واحد شديد الضعف؛ تعويضات الحماية لا تجعله آمنًا ولا متوافقًا مع توجيهات NIST |
| عمل هجين وفروع | خادم مرجعي ومحطات/خوادم فروع ومزامنة موثقة | لا يضمن العمل بلا اتصال قبول كل الحركات آليًا أو منع التعارض |
| ذكاء محلي وسحابي وهجين | واجهات موحدة للمزودين، موافقة وإعدادات خصوصية | النماذج تخطئ؛ دقة العربية اليمنية والمستندات بحاجة اختبارات حقيقية |
| ترحيل بعد موافقة المستخدم | مسودة ← تحقق ← معاينة ← اعتماد صريح ← ترحيل ذري | يجب التحقق مجددًا لحظة الترحيل إذا تغيرت البيانات أو الصلاحيات |
| إظهار العيوب | سجل أخطاء قابل للتتبع، لوحة صحة وخطوات استرداد | بعض التفاصيل الحساسة لا تُعرض للمستخدم غير المخول ولا تُسجّل بصيغة مكشوفة |

## 3. بحث السوق اليمني والمعايير: النتائج والحدود

1. يوجد انقسام في مناطق تداول الريال وأسعار الصرف؛ تذكر ACAPS/YETI منطقتين للنقد القديم في صنعاء والجديد في عدن، بينما يناقش البنك الدولي 2026 آثار التباين والنشاط المالي غير الرسمي [S1، S2]. لذلك تُسجّل **منطقة السوق ونوع النقد وسعر الصرف وتاريخ النفاذ والمصدر واتجاه السعر والمُدخل والمعتمد**. لا تُثبّت أسعار لحظية في الكود؛ ويُظهر النظام إذا كان السعر قديمًا أو غير مؤكد. سعر السوق ليس بالضرورة السعر المقبول محاسبيًا أو قانونيًا لكل عملية.
2. تُصمم القواعد الضريبية والفواتير كحزم قابلة للتحديث وذات تاريخ نفاذ ونطاق وتوثيق، لكن **لا تُفعّل نسبة أو إعفاء أو متطلبات فاتورة كحقيقة نهائية** قبل التحقق من النصوص السارية وقرارات الجهة المعنية وخبير محلي. النص القانوني التاريخي لدى منظمة التجارة مفيد كنقطة بداية، ولا يثبت وحده جميع التعديلات الحالية [S3]. يلزم استكمال مقابلات منشآت يمنية وخرائط عملياتها والحصول على تشريعات موثقة حسب المنطقة قبل الإطلاق.
3. IAS 21 يميز العملة الوظيفية وعملة العرض. عند انطباقه، تُحدد العملة الوظيفية بالوقائع الاقتصادية، ولا تتغير إلا بتغير تلك الوقائع؛ تطبق المعالجة الجديدة مستقبليًا من تاريخ التغيير مع الإفصاح المناسب [S4]. للمستخدم حرية اختيار عرض التقارير أو عملة المستند بحسب الصلاحية، أما تغيير العملة الوظيفية فله سير اعتماد مهني موثق، ولا يمحو التاريخ.
4. IFRS 18 يسري على فترات التقارير السنوية التي تبدأ في أو بعد 1 يناير 2027، مع السماح بالتطبيق المبكر حيث ينطبق؛ يجب تصميم تصنيفات التقارير والبيانات المقارنة مع مراجعة محاسب، وليس الادعاء أن مجرد إضافة عناوين تحقق الامتثال [S5]. المعايير لا تنطبق بالضرورة على كل محل؛ تُحدد السياسة المحاسبية المعمول بها لكل منشأة.
5. يعمل المنتج في واقع اتصال وكهرباء غير مستقرين محتملين، لكن لا توجد لدينا بعد دراسة ميدانية لأجهزة الفئات المستهدفة، أو أحجام معاملاتها، أو احتياجاتها الضريبية الفعلية؛ تُقاس في مرحلة الاكتشاف ولا تُختلق أرقام أداء.

## 4. المستخدمون والإعداد الأولي

**الأنواع المقترحة:** مالك، مدير نظام، مدير مالي، محاسب، مراجع، مسؤول فرع، مبيعات، مشتريات، مخزون، مستخدم قراءة، ومستخدم مخصص. هذه أدوار أولية قابلة للتعديل وليست صلاحيات نهائية.

**معالج الإعداد:**
1. نوع النشاط، الاسم القانوني والاسم التجاري، البلد، المنطقة، الرقم الضريبي إن وجد، الشكل القانوني.
2. إنشاء شركة أو مجموعة شركات وفروع ومخازن وصناديق وحسابات بنكية مع تعريف المالك القانوني لكل حساب.
3. السنة والفترات والإطار المحاسبي والإعدادات المحلية، مع تاريخ سريان كل سياسة.
4. تعيين العملة الوظيفية الموثقة، عملات المعاملات وعملة العرض، ومناطق أسعار الصرف ومصادرها.
5. دليل حسابات مناسب للنشاط، وحدات قياس وضريبة مهيأة بعد المراجعة، مراكز تكلفة وترقيم مستندات.
6. المستخدمون والأدوار وسياسة الدخول والموافقات وحدود الصلاحية، ومراجعة تحذيرات المخاطر.
7. أرصدة افتتاحية ومستندات مفتوحة وجرد، ثم ميزان مراجعة واعتماد قبل التشغيل.

**الهوية:** اسم العرض واسم الدخول يقبلان العربية وUnicode. يحتفظ النظام باسم عرض كما أدخل، وبمعرّف داخلي ثابت لا يتغير. تطبق قاعدة تطبيع Unicode محددة وقابلة للاختبار عند البحث والدخول، مع اكتشاف التصادم والرموز المتشابهة دون تغيير كلمة السر بصمت أو الخلط بين المستخدمين. سياسات الأسماء تسجل بوضوح.

## 5. خريطة الإدارات والواجهة

### الشاشة الرئيسية

واجهة RTL بعناصر بارزة وعمق وظلال على نحو الصور المرجعية، مع مراعاة التباين والوضوح. في الأعلى: الشركة والفرع، البحث العام، الإشعارات، اسم المستخدم، الحالة، إعدادات اللغة والمظهر. في الوسط بطاقات الإدارات التالية، لا تظهر غير المصرح بها:

- **المالية:** دليل الحسابات، القيود، اليومية، الأستاذ، مراكز التكلفة، سندات القبض والصرف، الصناديق والبنوك، التسويات، الفترات والعملات.
- **المبيعات والعملاء:** العملاء، عروض الأسعار، الطلبات، الفواتير والمرتجعات، التحصيل، الأعمار والتقارير.
- **المشتريات والموردون:** الموردون، طلبات وعروض الشراء، الاستلام، فواتير الموردين، المرتجعات، الدفع والأعمار.
- **المخزون:** الأصناف والوحدات والمخازن، الحركات والتحويل والجرد والتسويات والتقييم والأرصدة.
- **الأصول الثابتة:** سجل الأصل، الإضافة والتحسين والإهلاك والاستبعاد والتقارير.
- **الموارد البشرية والرواتب:** الموظفون والسياسات والرواتب والاستحقاقات، وفق قواعد محلية تُعتمد لاحقًا.
- **التقارير والتحليلات:** ميزان المراجعة، المركز المالي، الأرباح والخسائر، التدفقات النقدية، الضرائب ولوحات القياس.
- **المساعد الذكي:** المحادثات، المستندات، المهام والمسودات، الموافقات، الذاكرة والمزودون.
- **الإدارة والإعدادات:** الشركات والفروع، المستخدمون، الصلاحيات، التهيئة، النسخ والاتصال، صحة النظام والتدقيق.

البطاقات تقود إلى صفحة إدارة تضم أقسامًا وتبويبات واضحة، مع مسار تنقل، بحث، اختصارات، حالات تحميل وفراغ وخطأ. الأرقام المعروضة في أي عرض أولي يجب وصفها بأنها تجريبية ما لم تُقرأ من سجلات مرّحلة. للموبايل تتغير الشبكة بشكل متجاوب؛ تُحترم إعدادات تقليل الحركة وإمكانية التنقل بلوحة المفاتيح وقارئات الشاشة. الظلال والرسومات تُحسن دون جعلها شرطًا لسرعة الاستخدام.

### عقد البطاقة

`id، الاسم العربي، الوصف، الأيقونة/الأصل البصري، المسار، ترتيب العرض، الصلاحية، حالة التفعيل، الأقسام التابعة، إصدار العقد`. تُستخرج منها الواجهة والقائمة والبحث واختبارات الصلاحيات حيث يمكن، دون الادعاء أن إضافة إدارة جديدة تلغي الحاجة لكل منطق أعمال أو اختبار متخصص.

## 6. البنية التقنية المقترحة

```text
المتصفح / حاوية سطح مكتب اختيارية
        ↓ HTTPS / جلسة آمنة
Rust Web: توجيه + Askama + مكونات HTML + تفاعل JS محدود
        ↓ عقود أوامر ونتائج مهيكلة
التطبيق: هوية وصلاحيات | مالية | مبيعات | مشتريات | مخزون
        | تقارير | أصول | مساعد | مزامنة | إيصالات مشتركة
        ↓ حدود معاملة صريحة / مستودعات / صندوق أحداث Outbox
PostgreSQL مرجعي + تخزين مستندات مشفر + سجل تدقيق
        ↕ أوامر موقعة ومزامنة قابلة للتتبع
فرع محلي: خدمة Rust + قاعدة محلية + طابور آمن
        ↕ موصلات
Ollama / API سحابي / OCR / صوت / دفتر مشترك اختياري
```

- **Askama:** قوالب مترجمة وقت البناء وتستفيد من أنواع Rust [S6]. يقترح Axum/Tokio للخادم بعد تقييم متطلبات البيئة والتراخيص. العرض التفاعلي يحتاج JavaScript محدودًا أو مكتبة صغيرة بعد تقييم الأمان؛ لن تُفرض React.
- **التوزيع:** التطبيق الأساسي ويب محلي/مستضاف. حاوية Tauri اختيارية لسطح المكتب عند الحاجة، لا شرطًا لكل المستخدمين؛ يلزم اختبار قدرات النظام وWebView والتحديثات قبل اعتمادها [S7].
- **عزل النطاق:** تبدأ الإدارات كوحدات داخل نواة واحدة بعقود واضحة لتقليل التعقيد؛ استخراج خدمات منفصلة قرار لاحق مبني على قياس ومبرر.
- **البيانات:** PostgreSQL الخادم المرجعي، مع `NUMERIC` مقيد للدقة والنطاق. قاعدة فرع محلي مرشحة SQLite ضمن خدمة الفرع، مع تمثيل المبالغ كنص عشري أو أعداد صحيحة مضبوطة لا REAL؛ تقييم التحمل والتزامن والترحيل إلزامي. لا مشاركة ملف SQLite مباشرة بين أجهزة عبر مجلد شبكي.
- **العشرية:** تجربة `rust_decimal` بفرعه/إصداره المستقر المناسب [S8] مع فحص حدوده وأخطاء الفائض؛ إن لم تكف دقته تُقيّم مكتبة عشري أوسع. لا استخدام `f32/f64` كمرجع للحسابات المالية، ولا تحويل JSON المالي إلى أرقام ثنائية صامتًا.
- **البناء:** workspace بـ Cargo؛ تثبيت الإصدارات بالـ lockfile وبناء قابل للتكرار ومراجعة ثغرات ورخص وتحديثات منظمة. لا يُفترض أن الأحدث هو الأصلح دون اختبار.

## 7. العقد الموحد والتوليد الآلي

**مصدر حقيقة منطقي واحد لكل نطاق:** تعريفات نماذج Rust وقواعد المجال كمرجع للأنواع الثابتة، مع عقود API صريحة مولدة أو مطابقة آليًا، وتعريفات واجهة وتصاريح قابلة للإصدار. يجوز استخدام مخططات JSON Schema للمدخلات والذكاء والأدوات؛ يلزم التحقق من الاتساق بين المخطط وقواعد المجال باختبارات، لا افتراض أن التوليد وحده يمنع الانحراف.

**العقد القياسي لكل عملية:**
- هوية العملية والإصدار والنطاق والشركة والفرع والمستخدم والجهاز.
- مدخلات مكتوبة النوع، العملة، الدقة والقواعد، المستندات والحقول الإجبارية.
- الصلاحية والسياق والسياسات ذات التواريخ المناسبة.
- شروط التحقق، المخرجات، رموز الأخطاء والرسائل العربية، المعاينة والآثار الجانبية.
- مفتاح عدم التكرار، رقم الإصدار المتوقع، تعريف الموافقة والتدقيق.
- اختبارات العقد والخصائص والحالات الخاطئة والتوافق الخلفي والهجرة.

**مولد وحدة جديد:** أمر تطوير واحد ينشئ هيكل الوحدة والقوالب الأولية والتسجيل والصلاحيات والاختبارات وملف الهجرة، ويعمل في بيئة التطوير بعد مراجعة التغييرات؛ لا يطبق هجرة إنتاجية تلقائيًا. المطور يبقى مسؤولًا عن المنطق المالي وتدقيقه. أدوات `cargo fmt` و`clippy` و`test` وفحص التبعيات والهجرات وفحوص العقود ضمن مسار التحقق المستمر.

**تعارض المصدر:** لا تُكتب قائمة الصلاحيات والبطاقات وواجهات API يدويًا في أماكن متفرقة إن أمكن توليدها من سجل موحد مُراجع. عند تعذر التوليد نضع اختبار مطابقة يمنع البناء إذا اختلفت النسخ.

## 8. المحرك المالي والحياة الكاملة للترحيل

### ثوابت لا يجوز تجاوزها

1. القيد داخل كيان قانوني ودفتر محددين ومتوازن بالعملة الوظيفية: مجموع المدين = مجموع الدائن بعد سياسة التقريب المعلنة. يمكن قيود متعددة السطور ومتعددة العملات؛ لا يُفترض توازن كل عملة أجنبية بمفردها لكل قيد. أي قيد تقريبي أو فرق عملة يُنشأ بحساب معتمد وقاعدة صريحة.
2. المبالغ من نوع عشري معلوم الدقة والتقريب لكل عملة وسياق، مع اكتشاف الفائض والتحويل غير المقبول. تُخزن قيم المعاملة الأصلية، وسعرها، وقيمتها الوظيفية، وتفاصيل التقريب.
3. المسودات لا تؤثر على الدفتر. لا يُغيّر سطر مُرحل بصمت؛ التصحيح بعكس أو تعديل لاحق مرتبط، وفق سياسة الفترة. يُحفظ سجل الحركات الأصلية والتصحيحات [S9].
4. لا ترحيل في فترة مغلقة أو لشركة/فرع غير مخول إلا ضمن إجراء إعادة فتح أو تسوية مصرح ومسجل. التحقق من سلامة الحسابات والتواريخ والمستندات والصلاحيات قبل الترحيل وأثناءه.
5. ترحيل القيد والمستند وتحديث حالة الاعتماد وسجل التدقيق وحدث الـoutbox في معاملة قاعدة واحدة؛ كل أثر خارجي بعد الالتزام يُعالج بشكل قابل لإعادة المحاولة مع عدم تكرار. لا تُنشأ أموال فعلية بمجرد كتابة قيد.
6. نقطة مرجعية واحدة للتحقق؛ لا يعتمد النظام على الواجهة أو الذكاء الاصطناعي للتوازن أو الصلاحيات. عدم تكرار الطلب، فحص النسخة، وتحديد خطأ التعارض، ضرورية عند إعادة المحاولة والانقطاع.
7. استقلالية الشركات والفروع والقيود المتبادلة. سجلات التجميع والتوحيد والاستبعادات بين الشركات تحتاج نموذجًا خاصًا واعتمادات؛ لا تُدمج الأرصدة لمجرد تساوي الأسماء.

### التسلسل

`مسودة → تحقق مبدئي → معاينة مؤرخة ومبصمة → اعتماد صريح (بسيط أو متعدد حسب السياسة) → إعادة تحقق وفحص الإصدار → ترحيل ذري → إخطار وإيصال خارجي عند تفعيله`.

إذا تغير مبلغ أو سعر أو حساب أو مخزون أو صلاحية أو سياسة بعد المعاينة، تصبح الموافقة القديمة غير صالحة ويطلب النظام معاينة جديدة. بعض العمليات تتطلب فصل المُنشئ عن المُعتمد. مدة صلاحية المعاينة قابلة للضبط. رفض العملية يوضح السبب للمخول ويُحتفظ بالأثر حسب السياسة.

### مثال عددي توضيحي

بيع آجل بقيمة **100 دولار** من دون ضريبة، بسعر توضيحي **1,500 ريال وظيفي لكل دولار**: مدين العملاء 150,000 ريال، دائن المبيعات 150,000 ريال؛ ويحتفظ سطر العميل بمبلغ 100 دولار وسعر 1,500. عند التحصيل بسعر **1,600**: مدين النقدية 160,000، دائن العملاء 150,000، دائن ربح فرق صرف 10,000. المثال للتوضيح فقط؛ الأسعار غير حقيقية ولا تشمل المخزون أو الضريبة أو الاعتبارات المحلية. تحدد سياسة المنشأة المعالجة النهائية عند انطباق المعايير.

### نماذج البيانات الأساسية

`Tenant/Company/Branch`، `FiscalPeriod`، `Account`، `Currency`، `RateQuote`، `Journal` و`JournalLine`، `Document` و`Attachment`، `Counterparty`، `Item/Warehouse/StockMovement`، `Approval`، `AuditEvent`، `Identity/Role/Permission`، `SyncCommand`، `SharedReceipt`، `OutboxEvent`. كل كيان يحمل معرفًا ثابتًا ونطاقًا وإصدارًا وتواريخ ومرجع أثره؛ توضع الفهارس والقيود والمفاتيح الأجنبية حيث تناسب النطاق، مع اختبارات عزل الشركات.

## 9. العملات وأسعار الصرف

- **عملة المستند:** يختارها المستخدم المخوّل لكل حركة من العملات المفعلة.
- **عملة العرض:** يختارها المستخدم لتقارير أو شاشات وفق قواعد ترجمة مفصّلة ومصدر سعر ظاهر؛ لا تعيد كتابة القيود.
- **العملة الوظيفية:** تحدد عند إعداد الكيان مع حفظ المستند المهني. إذا انطبق IAS 21 فالتغيير مبني على تغير الوقائع، بموافقة وتاريخ سريان وخطة تحويل مستقبلية وإفصاح، دون إعادة كتابة الأصول التاريخية أو إيهام المستخدم بأن ذلك مجرد تفضيل [S4].
- **سعر الصرف:** زوج العملات واتجاه السعر، السوق ونوع النقد، تاريخ ووقت ومصدر وسريان، نوع السعر، المستخدم والاعتماد. عند غياب سعر أو وجود سعر قديم/متعارض تُعرض المشكلة ويُمنع الترحيل أو يُطلب الاستثناء المخوّل حسب السياسة. لا يستخدم النظام آخر سعر متاح بصمت.
- **إعادة التقييم والتسوية:** تقارير البنود النقدية وغير النقدية، فروق محققة وغير محققة حسب السياسة، اختبارات الفترات وحالات عدم قابلية التبادل. معالجة الفوارق والتوحيد بحاجة مواصفات محاسبية إضافية لكل حالة.
- **اليمن:** يمكن تعريف بعد تشغيلي للسوق ونوع النقد مع بقاء رمز ISO الرسمي YER كما هو؛ لا تُخترع رموز ISO أو تعامل أنواع النقد كعملات قانونية مستقلة دون أساس مهني وتنظيمي. تحويل النقد بين المناطق يحتاج نموذجًا محاسبيًا وقانونيًا يعتمد على الواقع الفعلي.

## 10. القيد الثلاثي والإيصال الموزع

### النموذج المقترح

يسجل كل طرف قيده المزدوج في دفاتره المستقلة. ينشأ إيصال مشترك لواقعة متفق عليها يحتوي إصدار العقد ومعرف المعاملة والطرفين ومرجع المستند والمبلغ والعملة والطابع الزمني والمنطقة وتعهدات التوقيع، مع بصمات البيانات ذات الصلة بدل نشر الوثائق أو أسرار العملاء. يوقعه الأطراف المفوضون، ويُودع إثباته في سجل موزع مرخّص تديره **أطراف مستقلة فعلًا** وفق سياسة عضوية وخصوصية وتحقق وتوافق معلنة. Hyperledger Fabric خيار للتقييم وليس قرارًا نهائيًا [S10].

**حالات الإيصال:** لم يُنشأ ← بانتظار التوقيع ← موقع جزئيًا ← موقع من الأطراف المطلوبة ← بانتظار إيداع السجل ← مثبت وقابل للتحقق / متنازع عليه / فشل إيداع / ملغى أو مصحح بإيصال لاحق. تحفظ المرجعية القانونية وسلسلة التصحيح، ولا يتظاهر النظام بأن الفشل نجاح.

**الفصل بين الترحيل والتوزيع:** يحدث الترحيل المحلي وفق سياسة الاعتماد، ثم يتولى outbox الإرسال للسجل المشترك؛ في حال فشل الاتصال يظل القيد المحلي مرحلًا وحالة الإيصال معلقة بوضوح. إذا اشترطت المنشأة الإثبات المشترك قبل اعتماد العمل تجاريًا، تضبط حالة العملية والسياسة وفق ذلك؛ لا تُستخدم معاملة قاعدة بيانات موزعة وهمية ولا يعد النظام بأن النتيجتين ذريتان بلا تصميم مثبت. إعادة المحاولة تعتمد معرفًا ثابتًا وتمنع الازدواج.

**تصحيح التصورات المهمة:**
- التوقيع يثبت أن حامل المفتاح وقّع بيانات محددة، وليس أن البضاعة موجودة أو أن البيان صحيح أو عادل أو قانوني. كشف التناقض يتوقف على مشاركة السجلات والتحقق وإتاحة البيانات.
- السجل يجعل العبث أصعب وقابلًا للاكتشاف ضمن نموذج الثقة، لكنه ليس مستحيل التلاعب مطلقًا، ولا يحل مشكلات اختراق المفاتيح، تواطؤ الأغلبية أو مدخلات خاطئة.
- لا يلغي الحاجة للمراجع الخارجي أو الرقابة القانونية؛ قد يقلل أعمال مطابقة معينة. العقود الذكية لا تحرك أموال البنوك تلقائيًا إلا بوجود تكامل دفع مرخص وصلاحيات وضمانات؛ اعتماد المستخدم مطلوب حسب السياسة.
- إن كانت جميع العقد تحت سيطرة جهة واحدة فذلك ليس توزيعًا مستقلًا؛ يُعرض ذلك كتدقيق محلي/شبكة داخلية، لا كضمان ضد تعديل طرف منفرد. يجب تحديد الأطراف، الحوكمة، المفاتيح، الاسترداد، الاحتفاظ والاختصاص القانوني قبل الإطلاق.

## 11. المساعد الذكي والخصوصية

**مسار مقترح:** إدخال نص/صوت/مرفق ← تحويل إلى نص واستخراج أولي مع إظهار المصدر والثقة ← تحديد النية والحقول الناقصة ← اقتراح أدوات محددة بعقود JSON Schema ← تحقق حتمي وصلاحيات ونطاق ← فتح الشاشة أو إنشاء مسودة ← عرض القيد والأثر والمستندات والسعر ← موافقة مستخدم مخول ← خدمة الترحيل تتحقق مجددًا. للمساعد صلاحيات المستخدم لا أكثر، ولا وصول مباشر لقاعدة البيانات أو لتنفيذ أوامر نظام أو أدوات غير مصرح بها.

- **المزود:** موصل Ollama المحلي أو مزود سحابي من اختيار المنشأة أو توجيه هجين بسياسة واضحة؛ لا يُرسل مستند أو بيانات حساسة للسحابة دون تمكين مسبق ونطاق واضح. انقطاع المزود لا يوقف العمليات اليدوية. Ollama يدعم tool calling ومخرجات منظمة [S11]، لكن الدعم والجودة يعتمدان على النموذج.
- **المستندات:** OCR/رؤية لفواتير PDF وصور، ثم إسناد لكل حقل إلى موضعه الأصلي متى أمكن، وعرض الحقول المشكوك فيها وتأكيدها. فحص نوع وحجم الملف وملحقاته، والفيروسات عند توفر أداة موثوقة، وفصل المرفقات عن التنفيذ. تعليمات داخل المستند أو المحادثة تعامل كبيانات غير موثوقة لا صلاحيات.
- **الصوت:** تقييم whisper.cpp للتفريغ المحلي [S12] ونموذج صوت عربي مفتوح مناسب للرد، مع فحص ترخيص كل نموذج لا البرنامج فقط. تُختبر اللهجة اليمنية والأرقام والعملات والضوضاء؛ تتطلب الأرقام والتواريخ الخطرة تأكيدًا مرئيًا. لم يتم اختبار جودة أي صوت محلي في هذه الوثيقة.
- **الذاكرة:** سياق قصير داخل الجلسة، وذاكرة طويلة بإذن صريح لكل منشأة ومستخدم مع تصنيفات ومدة احتفاظ وإمكانية عرض وتصحيح وحذف المسموح؛ فصلها عن السجل المالي الذي قد تخضع مدة الاحتفاظ به لالتزامات. لا تدريب تلقائي أو تخزين الأسرار على أساس «التعلم من كل شيء». التفضيلات والاقتراحات لا تغير قاعدة محاسبية أو صلاحية تلقائيًا.
- **التحذيرات:** هلوسة، حقن التعليمات، تسريب عبر المزود، استخلاص خاطئ وأرقام مضللة. الأثر المالي يظل نتيجة محرك حتمي واختبارات، وليس قرار النموذج.

## 12. الأمن وكلمات المرور والصلاحيات

يدعم النظام اختيار كلمة مرور من حرف واحد أو رقم واحد أو أكثر، دون فرض حد أدنى يزيد على محرف واحد ودون اشتراط نوع المحارف، وفق قرار صاحب المشروع. تقبل العربية وUnicode وكلمات المرور الطويلة واللصق. تُخزن كلمة المرور بأمان ولا يمكن استرجاع نصها الأصلي. ملاحظة مهنية: كلمة المرور القصيرة أكثر عرضة للتخمين، وهذا الاختيار لا يطابق الحدود المذكورة في توجيهات NIST [S13].

**التصميم المعتمد للمتطلبات:** حرية اختيار كلمة المرور قائمة لجميع المستخدمين دون إلزام بعامل ثانٍ أو حظر المناصب الحساسة أو قصر الميزة على استثناء. تعرض نصيحة أمنية مختصرة عند الاختيار من غير منع، مع حماية الهاش وتقييد المحاولات وتسجيل محاولات الدخول وسياسات الجهاز والشبكة. تبقى وسائل الحماية الإضافية خيارات قابلة للضبط وليست شرطًا لاستخدام كلمة قصيرة.

- تخزين السر بهاش Argon2id مع ملح مستقل، وضبط التكلفة بحسب OWASP واختبارات الأجهزة [S14]؛ لا تخزين كلمات السر أو مفاتيح API في السجلات أو النص الواضح. خزينة أسرار ونظام تشغيل أو خدمة مفاتيح، وتدوير/إبطال/استرداد مُختبر.
- الصلاحيات على مستوى الشركة والفرع والإدارة والفعل والسجل عند الحاجة، وحدود المبالغ، الفصل بين المهام، منع التصعيد، المصادقة المتجددة للعمليات الحساسة. يفحص الخادم الصلاحية في كل طلب وكل أداة ذكاء اصطناعي.
- TLS، جلسات آمنة وCSRF وقواعد XSS ورفع ملفات وترويسات أمنية، تحديثات موقعة، وسياسات شبكة وفصل بيئات. يعتمد تصميم التشفير على نماذج تهديد ومراجعة متخصصة وليس خوارزميات مبتكرة منزليًا.
- سجلات تدقيق قابلة للتحقق، مع مراقبة محاولة التعديل، ونسخ إثبات مستقلة. البصمات المحلية وحدها لا تمنع مسؤول النظام من إعادة كتابة السجل كله. إخفاء الأسرار والبيانات الحساسة وتقييد الوصول للتفاصيل.

## 13. الفروع والانقطاع والمزامنة

**نموذج مبدئي:** خدمة مركزية مرجعية لكل مجموعة تشغيل، وخدمة فرع محلية بمخزن مستقل وطابور أوامر موقعة. يمنح النظام كل أمر معرفًا ثابتًا ونسخة الموارد وتاريخ الحدث وتاريخ الاستقبال وهوية الفرع والجهاز. إعادة إرسال نفس المفتاح لا تنشئ عملية ثانية.

- عند الاتصال: المصادقة، تبادل الإعدادات والإصدارات، إرسال الأوامر بترتيب السببية، تحقق المركز من الصلاحيات والقواعد المتفق عليها، ثم قبول أو رفض مفصل، وتحديث الحالة في الفرع. التواريخ لا ترتب وحدها بسبب انحراف الساعات.
- أثناء الانقطاع: يُسمح بعمليات محددة في سياسة معتمدة فقط، ويظهر بوضوح هل هي **مسودة محلية، مرحّلة محليًا بانتظار قبول المركز، مقبولة مركزيًا، أم مرفوضة/متعارضة**. لا تُظهر الأرصدة على أنها موحدة لحظيًا دون تأكيد.
- التعارضات لا تُحل بمنطق «آخر تعديل يفوز» للأموال أو المخزون. أمثلة: عميل مكرر، رقم فاتورة مكرر، صرف رصيد مشترك، بيع مخزون متزامن، فترة أغلقت، إلغاء صلاحية، تغيّر سعر. الحل يكون عبر حجز موارد مسبق أو صلاحيات وتخصيص أرصدة للفرع أو تعليق/تسوية صريحة، مع توضيح أن السياسات تقيد التشغيل غير المتصل.
- إذا سبق قبول الفرع عملية ورفضها المركز، لا يُمحى أثرها؛ تظهر مهمة استثناء وتسوية مرتبطة يوافق عليها المخول. صمم استمرارية العمل مع تحليل أثر قانوني وفترة التقارير. تتطلب هذه المنطقة اختبارات محاكاة مكثفة وموافقة على نموذج الالتزامات قبل الإنتاج.

## 14. الأخطاء، التشغيل، النسخ والاسترداد

- كل خطأ له رمز ثابت ورسالة مفهومة وإجراء مقترح ومعرف تتبع؛ الأخطاء التشغيلية تظهر في لوحة الصحة بحسب الصلاحيات. لا فشل صامت، ولا إظهار أسرار أو أثر تقني حساس للمستخدم العادي. بعض الحالات الحساسة مثل تفاصيل فشل المصادقة تُعرض بشكل عام عمدًا لتقليل كشف المعلومات، وتسجل تفاصيلها آمنًا للمخول.
- حالات مراقبة: تعطل قاعدة البيانات، فشل المزامنة، نفاد مساحة، فشل نسخة، فشل إيصال مشترك، سعر قديم، توقف مزود الذكاء، خطأ استخراج، انتهاء شهادة، رفض الصلاحية، عملية مكررة، تأخر مهام outbox.
- نسخ مشفرة دورية محلية وخارجية وفق سياسة المنشأة، إدارة مفاتيح مستقلة، اختبار استعادة فعلي ودوري، حماية من الفدية وتسجيل النتائج. تُحدد RPO وRTO بعد معرفة بنية العميل؛ لا يُدّعى تحقيقهما دون اختبار.
- هجرات بإصدار، نسخة احتياطية واختبار مسبق، توافق الإصدارات للفرع والمركز، وخطة رجوع/استرداد تعتمد نوع الهجرة؛ بعض هجرات البيانات لا يمكن عكسها تلقائيًا.

| Ollama | تنفيذ محلي ونموذج أدوات وبيانات منظمة [S11] | كل نموذج وعتاد يختلفان؛ لا ثقة تلقائية بالمخرجات |
| whisper.cpp | مرشح تفريغ صوت محلي [S12] | العربية اليمنية، الأداء، وترخيص الأوزان تُختبر لكل نموذج |
| Hyperledger Fabric | دفتر مرخص للأطراف المستقلة وتقييم الخصوصية والعضوية [S10] | موارد وحوكمة وتعقيد؛ ليس لازمًا للمحل الصغير ولا خيارًا نهائيًا |

الترخيص المجاني لا يعني انعدام تكلفة الخوادم أو التشغيل أو النماذج أو الدعم. التحقق النهائي من إصدارات كل مكتبة، سلامتها، صيانتها وترخيصها وترخيص نماذجها يتم عند التنفيذ؛ لم تُنزّل أو تُختبر هذه الأدوات لهذا المخطط.

## 16. خطة التنفيذ وبوابات القبول

**0 — اكتشاف واعتماد:** مقابلات وحالات استخدام يمنية، تشريعات صادرة قابلة للتحقق، أحجام وعتاد، تعريف أصحاب المصلحة، سياسات قبول المخاطر وهوية الأطراف المستقلة. **المخرج:** مواصفات موقعة ومجموعة أمثلة محاسبية من خبير.

**1 — الأساس:** مستودع Rust/Askama، إعداد الشركة والمستخدم، بطاقات حقيقية بصلاحيات، دليل الحسابات، الفترات، عملات وأسعار، قيود يدوية بمسودة واعتماد وترحيل وعكس، ميزان مراجعة، سجل تدقيق وأخطاء. **بوابة:** اختبارات التوازن، الدقة، الصلاحيات والعكس وعدم التكرار والاستعادة تمر، ومراجعة محاسب؛ لا بيانات إنتاج قبل المراجعة.

**2 — المبيعات والمشتريات والمخزون الأساسي:** عميل/مورد/صنف، فاتورة بيع وشراء وسداد ومرتجع، محاسبة المخزون والسياسات المتفق عليها وتكامل ترحيل متسق. **بوابة:** حالات من أول المستند حتى القيود والتقارير والتسوية والمخزون والضرائب المختبرة لكل سياسة مفعلة.

**3 — المساعد:** محادثة نصية ثم المستند والصوت، موصل Ollama، سحابي مشروط، عقود أدوات، مسودات وموافقة، ثم الذاكرة وفق السياسة. **بوابة:** اختبارات الأرقام العربية اليمنية والمرفقات والحقن ورفض الصلاحيات وعدم الترحيل دون اعتماد.

**4 — الهجين:** خدمة الفرع والطابور وقواعد التعارض والاسترداد. **بوابة:** محاكاة انقطاع ومزامنة متكررة وتعارض مخزون وفترة وصلاحية وإثبات أن الحالات المعلقة ظاهرة.

**5 — القيد الثلاثي:** اتفاقية أطراف، هوية رقمية وتوقيعات، شبكة مرخصة وتجريب الإيصالات والتصحيح والتحقق المستقل. **بوابة:** تحقق من الطرف الآخر وفقد المفاتيح والتلاعب والفشل والخصوصية؛ تعرض المطالبات الأمنية بحدودها.

**6 — التوسع:** أصول ورواتب وتقارير متقدمة ومجموعة شركات وإضافات. كل إدارة لا تُعلن جاهزة إلا بعد اختبار قواعدها وتشغيلها ومراجعتها.

التسلسل أعلاه ترتيب هندسي لضبط المخاطر، وليس تجزئة لإخفاء أجزاء ناقصة؛ تُتابع كل مرحلة على لوحة حالة علنية للمالك. لا يوجد جدول زمني أو تكلفة موثوقان قبل تقدير الفريق والنطاق والبيئة.

## 17. اختبارات ومعايير قبول عملية

1. **خواص الحساب:** توليد قيود عشوائية وتحقق التوازن، خاصية العكس، الفائض، السالب، التقريب، اختلاف المقاييس، حد المبالغ، العملات الأجنبية، إعادة تشغيل نفس الطلب.
2. **سير الموافقة:** مسودة لا تؤثر؛ رفض مستخدم غير مخوّل؛ إعادة المعاينة بعد تعديل المبلغ؛ تغيير الصلاحية قبل الترحيل؛ اعتمادان متزامنان ينتجان أثرًا واحدًا.
3. **الحالات اليمنية:** تسجيل أسعار متعددة بحسب السوق والنقد والتاريخ؛ لا استخدام سعر قديم دون تنبيه؛ فواتير وإعفاءات من أمثلة محاسب محلي موثقة، لا من أرقام متخيلة.
4. **التدقيق والاسترداد:** لا تعديل للمُرحل من التطبيق؛ ربط قيد العكس؛ استعادة نسخة في بيئة معزولة والتحقق من ميزان المراجعة والمرفقات وسجل التدقيق.
5. **العزل والأمن:** اختبارات وصول بين الشركات والفروع، عربية Unicode والتصادم، XSS/CSRF، رفع ملفات ضارة، تقييد المحاولات، عدم تسرب الأسرار، اختبارات اختراق مستقلة قبل الإنتاج.
6. **المساعد:** وثيقة تحتوي أمرًا خبيثًا لا يغير الصلاحيات؛ استخلاص خطأ يعرض مصدره ويطلب مراجعة؛ لا دفع أو ترحيل بلا اعتماد؛ فشل المزود يترك المسودة واضحة.
7. **المزامنة والإيصال:** إعادة إرسال 100 مرة لا تكرر، انقطاع أثناء الالتزام، تعارض أرصدة، إيصال بتوقيع خاطئ، عقدة متوقفة، حالة معلقة مرئية، تصحيح موثق. الاختبار وحده لا يثبت أمان النظام بالكامل.
8. **الأداء والإتاحة:** توضع أهداف رقمية بعد قياس أجهزة واتصالات اليمن والحمولة الفعلية؛ تقاس أزمنة الاستجابة وحجم الذاكرة وسلوك الانقطاع وإمكانية الوصول. لا أرقام مختلقة في هذه المرحلة.

## 20.2 التجارة الاجتماعية وإدارة القنوات

### أ. النطاق المقصود

إضافة بطاقة **«التجارة الاجتماعية»** تفتح صندوق محادثات موحدًا، جهات اتصال وربطها بالعملاء بموافقة، المنتجات والأسعار المتاحة، العروض، الطلبات، حالة الشحن، قوالب الرسائل، الحملات المصرح بها، التحليلات والإعدادات. تُفعّل كل قناة بحسب الترخيص والصلاحية وبشكل مستقل لكل شركة/فرع. البداية المقترحة: **WhatsApp Business Platform Cloud API** و**Facebook Messenger للصفحات**؛ ثم Instagram Professional حيث تسمح واجهة Meta والتراخيص والصلاحيات. القنوات الأخرى تضاف بموصل مستقل بعد التحقق من واجهتها وشروطها، ولا يفترض أن «وغيره» متصل تلقائيًا.

سيناريو: رسالة عميل ← إثبات القناة والموافقة ← إنشاء محادثة أو ربط مقترح بعميل ← اقتراح أصناف وأسعار ومخزون ← عرض سعر/طلب **مسودة** ← تأكيد المصرح له حسب سياسة الشركة ← استكمال دفع أو تسليم عبر تكاملات مستقلة إن توفرت ← فاتورة ومعاينة قيد ← اعتماد بشري قبل الترحيل. لا تعني الرسالة أو صورة إثبات تحويل أن المال وصل أو أن الطلب مدفوع؛ التحقق البنكي أو اعتماد المخول مطلوب.

### ب. معالج الإعداد وإزالة التعقيد

يُصمم النظام لتجهيز الموصلات ومعالج الربط والتشخيص والقوالب وتدفقات الإعداد مسبقًا، بحيث لا يكتب العميل أكوادًا. بعد التنفيذ الفعلي تقتصر أعماله قدر الإمكان على:

1. اختيار القناة والشركة والفرع ومن يحق له الاطلاع؛ قبول شروط الاستخدام والخصوصية.
2. ربط حساب الأعمال/الصفحة عبر طريقة تفويض رسمية حيث تتاح، أو إدخال المعرفات والرموز اللازمة في خزينة مشفرة؛ عدم طلب كلمة مرور Facebook أو WhatsApp داخل النظام.
3. إعداد رقم الأعمال أو الصفحة، التفويضات والأذونات، عنوان استقبال الأحداث والتحقق منه، وسياسة القوالب وموافقة العملاء، والعملة/الأسعار ومخازن البيع والردود.
4. اختبار الاتصال والأذونات واستقبال حدث تجريبي وإرسال رسالة اختبار مسموحة؛ إظهار الحالة مع السبب وطريقة المعالجة، وتجديد الرموز وتفعيل التنبيهات.
5. ربط الرسائل والطلبات بالمنتجات وإعداد مسار الاعتماد وسياسات الأسعار والخصومات والمخزون، ثم مراجعة التكلفة وموافقة العميل على التشغيل.

قد يلزم حساب مطور، مراجعة التطبيق من Meta، التحقق من النشاط التجاري أو رقم الهاتف، صلاحيات صفحة، موافقة على قالب، خدمة مزود أعمال أو رسوم، بحسب نوع الربط وسياسات المنصة والبلد. المسار المضمن Embedded Signup ليس متاحًا تلقائيًا لكل بائع برمجيات ويجب التحقق من الأهلية أو العمل مع مزود معتمد. واجهة Messenger الرسمية تذكر التفويض والمراجعة ومحددات التفاعل واشتراطات حساب الصفحة [A3]. لا نعد بأن إدخال الروابط وحده يكفي لكل عميل، ولا بأن Meta تقبل كل طلب أو أن الخدمة تعمل بلا انقطاع.

### ج. المعمارية والاعتمادية

`منصة القناة ← HTTPS webhook/بوابة عامة موثوقة ← تحقق توقيع + إسناد الشركة ← تخزين حدث دائم سريع ← طابور ← موصل القناة ← صندوق المحادثات/عقد طلب`.

- إذا كان خادم العميل داخل شبكة محلية بلا عنوان عام أو اتصال، يحتاج استقبال Webhooks إلى **بوابة سحابية عامة آمنة** أو بنية تعرض نقطة نهاية عامة على نحو موثوق. تظل الرسائل في انتظار المزامنة عند انقطاع الفرع وفق حدود ومدة احتفاظ معلنتين؛ لا يمكن استقبال حدث مباشر من Meta بجهاز غير متصل.
- لكل حدث معرف مزود ومعرف قناة وشركة، والتحقق من التوقيع والجهة والتوقيت حسب الوثائق، ورد سريع بعد تخزين مضمون، وإعادة محاولة ذات حدود وbackoff وDLQ للرسائل الفاشلة. يعالج النظام تكرار الإشعارات ووصول الحالات بترتيب مختلف دون تكرار طلب أو رسالة.
- معرّفات العملاء عبر المنصات لا تعني تطابق الهوية تلقائيًا. أي دمج يحتاج قاعدة مطابقة قابلة للتفسير أو تأكيدًا؛ يُمنع خلط بيانات الشركات. الصندوق يدعم تعيين الموظف والتحويل البشري، وتاريخ المحادثة وحدود الوصول.
- حالات الرسائل: مسودة، مجدولة، في الانتظار، أُرسلت لمزود الخدمة، سُلّمت/قُرئت عند الإبلاغ، فشلت/مرفوضة. نجاح API ليس ضمانًا لتسليم الرسالة. الحملات تحتاج موافقة العميل المستلم وسياسة إلغاء اشتراك وسقف تكاليف؛ لا إرسال عشوائي أو التفاف على حدود المنصة.
- القوالب ونوافذ التواصل وقيود الترويج والرسوم والإصدارات يحكمها كل مزود وتتغير؛ تُراجع قبل التنفيذ وعند كل تحديث، وتُعرض القيود والتكلفة التقديرية أو غير المعروفة بدل تثبيت سعر أو الإيحاء بأن الخدمة مجانية.
- تُخزن الرموز في خزينة وتُحدّد نطاقاتها ومدتها؛ تُختبر دورة الإلغاء والتجديد، وتُسجل الأحداث المهمة دون نصوص حساسة أو رموز. أسماء الحسابات ومحتوى العملاء يخضعان لسياسة خصوصية واحتفاظ متفق عليها.

### د. اختبارات القبول

حسابات اختبار حقيقية، فشل ربط وتفويض وموافقة وقالب، توقيع مزيف، تكرار 100 حدث، حدث يصل متأخرًا، رمز منتهي، طلب متكرر، تعطّل البوابة وانقطاع الفرع، سوء إسناد صفحة لشركة أخرى، رسالة تتجاوز حدود المنصة، وإعادة التشغيل بعد تعطل المعالج. يتحقق الاختبار من عدم صدور قيد بلا اعتماد وعدم اعتبار «أُرسل» = «سُلّم». الاختبار على بيئة Meta التجريبية أو حسابات يملكها العميل/المشروع بعد منح التفويض، لا على حسابات وهمية يُدّعى تشغيلها.

## 20.3 المساعد السياقي والملء التلقائي

يُضاف **محرك سياق مصرح** يعرض للمساعد فقط ما يحق للمستخدم قراءته: معرف الشاشة والحقول ذات الصلة ومحتواها، الشركة والفرع، دور المستخدم، اللغة والمنطقة الزمنية، الحالة المعلنة للمستند، والرسائل المرتبطة المسموح بها. قراءة النوافذ تعني قراءة بيانات واجهات النظام المهيكلة عبر عقد سياق؛ لا تعني تصوير الشاشة أو تسجيل ضغطات المفاتيح أو مراقبة تطبيقات أخرى. تُستبعد كلمات المرور والأسرار والحقول المخفية؛ يمكن إيقاف السياق وتقليل البيانات، ويُظهر النظام ما أُرسل للمزود السحابي قبل تفعيله.

**آلية التعبئة:**
1. المدخلات من اختيار صريح، البيانات المسموح بها، تاريخ سياقي، قواعد المنشأة أو اقتراح نموذج. يحتفظ كل حقل بمصدره ووقت اقتراحه وحالة ثقة أو سبب؛ لا تُعرض الثقة الرقمية كاحتمال دقيق دون معايرة.
2. الحقول غير الحساسة قد تقترح تلقائيًا؛ الحقول الحساسة مثل المبلغ والحساب والعملة والسعر والضريبة والعميل والمستودع والخصم ووجهة الدفع تظهر كاقتراحات واضحة قابلة للمراجعة، وتُطلب المصادقة/الموافقة حيث تقتضي السياسة. لا يطغى اقتراح تلقائي على قيمة أدخلها المستخدم دون إذنه.
3. إذا اختلفت بيانات النافذة عن المحادثة، أو كان الكيان ملتبسًا، يسأل النظام بدل التخمين. التاريخ والوقت ليسا وحدهما دليلًا لإنشاء أو تأريخ أو ترحيل حركة؛ تاريخ المستند يحدده المستخدم أو سياسة موثقة مع عرضه.
4. لا يتخذ المساعد قرارات نهائية بشأن المدفوعات أو الاعتماد أو الترحيل، ولا يوسع صلاحيات المستخدم. جميع الأوامر تمر عبر العقود والتحقق الخادمي، مع إعادة التحقق من المخزون والأسعار والصلاحية عند التنفيذ.
5. تعلم التفضيلات يتم بإذن وسياسة احتفاظ واضحة، ويُراجع ويُحذف ضمن ما تسمح به المتطلبات القانونية؛ لا يُدرّب النموذج على بيانات عميل أو يرسلها لمزود سحابي افتراضيًا.

**اختبارات:** عدم تسريب كلمات السر أو بيانات شركة أخرى؛ عدم تغيير مدخلات المستخدم؛ طلب توضيح الاسم المتشابه؛ توقع التاريخ مع إظهار مصدره؛ منع الترحيل عبر أوامر المحادثة؛ كشف تعليمات خبيثة في فاتورة؛ قياس دقة الاقتراحات العربية واللهجة اليمنية على عينات معتمدة.

## 20.4 لوحة مهندس النظام وحماية حقوق صاحب المنتج

### أ. لوحتان منفصلتان

**لوحة المورّد/المهندس:** إدارة التراخيص والنسخ والباقات والإصدارات والأجهزة/التفعيلات، الوكلاء والعقود وحالة الدعم والتحديثات والتشخيص ضمن الصلاحية. تُحمى بحساب مهندس مستقل وكلمة سر خاصة يختارها صاحب النظام، ويُتاح تشغيلها من الجهاز المحلي المخصص للصيانة دون اشتراط وصول عن بُعد أو عامل ثانٍ. يفضل عدم تضمين كلمة سر ثابتة موحدة في الشيفرة أو جميع النسخ. إصدار الترخيص وتغيير إعدادات الوصول صلاحيتان منفصلتان. يُسجل كل دخول وإجراء مع تنبيه ومراجعة، وتُحمى مفاتيح التوقيع في خدمة/خزينة منفصلة مع خطة تدوير واسترداد.

**لوحة إدارة منشأة العميل:** يملكها العميل؛ تدير مستخدميه وإعداداته وموافقات الدعم وحدود البيانات. ملكية منتجك لا تعني ملكية بياناته، ولا ينبغي أن تتمكن لوحة المورد من تجاوز موافقات العميل سرًا. تفاصيل العلاقة يحددها العقد والقانون المناسبان.

### ب. فتح النوافذ والحسابات واسترداد الدخول

يمكن للمهندس، بعد تسجيل دخوله الخاص محليًا على الجهاز المخصص، فتح أي نافذة أو حساب ضمن صلاحيات الصيانة الممنوحة له وتقديم الدعم، مع تسجيل الإجراءات المهمة. لا يُشترط اتصال عن بُعد أو موافقة جديدة لكل نافذة. تفاصيل التفويض المحلي ومدة الجلسة تُضبط وفق إعداد المنشأة وعقد الدعم:

1. يبدأ المهندس جلسة صيانة محلية بكلمة سره الخاصة، ويختار الشركة والحساب والنافذة. يظهر وضع الصيانة بوضوح، وتُسجل هوية المهندس والوقت والإجراءات، ويمكن إنهاء الجلسة. لا يتطلب فتح كل نافذة موافقة جديدة.
2. لا تُكشف كلمة المرور القديمة: تخزن كهاش ولا يمكن استرجاعها من النظام. لاسترداد اسم مستخدم، يتحقق موظف الدعم من هوية الشخص وملكيته ثم يعرض المعرّف المصرح به أو الاسم المقنع؛ لاسترداد الدخول يصدر رابط/رمز استرداد محدود أو إعادة ضبط من مدير العميل، ويختار المستخدم سرًا جديدًا. تُلغى الجلسات القديمة بحسب السياسة.
3. عند فقد كل مديري العميل: إجراء طوارئ موثق مع إثبات ملكية المنشأة وهوية المخولين ومراجعة طرفين أو رموز استرداد سابقة، ثم إنشاء مدير جديد أو إعادة ضبطه؛ يُرسل إشعار للمخولين ويُحفظ الدليل. في وضع غير متصل يستخدم تحديًا وجوابًا موقّعين أو مفاتيح استرداد لدى العميل بعد التحقق، دون مفتاح خاص للمورد داخل النسخة.
4. يتيح وضع المهندس فحص الحسابات والنوافذ وصيانتها محليًا. لا يؤدي فتح الحساب إلى ترحيل مالي تلقائي؛ الترحيل والتغييرات المالية تتبع صلاحياتها وقواعد الاعتماد وسجل التدقيق. تظهر هوية المهندس عند العمل على حساب مستخدم بدل إسناد عمله إلى المستخدم بصمت. لا سبيل هندسي أمين يضمن استرجاع بيانات مشفرة إذا فقد العميل جميع مفاتيح الاسترداد؛ يحدد العقد خطة الحفظ والنسخ.

ملاحظة مهنية: الوصول من نفس الجهاز يقلل التعرض عن بُعد لكنه لا يمنع الوصول غير المصرح به للجهاز أو تسرب كلمة سر مشتركة. لذلك يوصى بكلمة مهندس فريدة لكل تثبيت أو وسيلة قابلة للتغيير، وتسجيل الصيانة، وحماية الجهاز [A4].

### ج. الترخيص والتفعيل والملكية الفكرية

- خدمة تراخيص مستقلة توقّع استحقاقات تتضمن معرف العميل والترخيص والنسخة/الباقة والوحدات والحدود وتواريخها ونسخة المفتاح؛ يتحقق البرنامج محليًا بمفتاح عام فقط. **مفتاح التوقيع الخاص لا يشحن مع نسخة العميل**. يُراجع استخدام توقيعات Ed25519 أو بديل ملائم للمكتبات والقيود التشغيلية؛ لا تُخترع خوارزميات خاصة.
- دعم الترخيص الدائم أو الاشتراك حسب العقد؛ التفعيل الإلكتروني أو إصدار ملف ترخيص موقّع لبيئات غير متصلة. ربط الجهاز اختياري ومتناسب؛ تغيير عتاد العميل له مسار نقل واسترداد، ولا يعتمد على بصمة جهاز كسرية غير مستقرة بوصفها سرًا.
- تُحدد مهلة الانقطاع والإنذار والتجديد مسبقًا وتظهر بوضوح. الإلغاء أثناء انقطاع دائم لا يصل للعميل فورًا، ويمكن التلاعب بساعة الجهاز؛ هذه حدود حقيقية. توقيع الترخيص يحمي من تزوير البيانات لكنه لا يمنع مهاجمًا يتحكم في جهازه من تعديل كود التحقق محليًا [A5].
- عدم حذف أو تشفير بيانات العميل كعقوبة أو تعطيل القدرة على قراءة السجلات وتصديرها عند انتهاء الترخيص؛ تُحدد القيود الأخرى على الوحدات بموجب عقد واضح، مع استمرار النسخ والتدقيق وآلية الدعم والتسوية. يُفصل استحقاق الترخيص عن صلاحية الاطلاع على بيانات العميل.
- اتفاقية ترخيص تجارية، شروط تحديث ودعم ونسخ وحفظ بيانات، عقود عمل/نقل حقوق للكود والتصميم، تسجيل العلامة حيث يلزم، سجل ملكية وSBOM، ومراجعة تراخيص المكتبات والنماذج قبل البيع والتوزيع. مفتوح المصدر لا يعني حرية إغلاق كل مكون أو إعادة توزيعه بلا التزام. يستلزم هذا مراجعة محامٍ مختص وليس ضمانًا قانونيًا من هذه الوثيقة.
- نسخ احتياطية للمفاتيح الخاصة في خزائن منفصلة، وتدوير المفاتيح وآلية إبطال وإصدار بديل موثق؛ لا تسجل مفاتيح الترخيص أو أسرار العملاء في مستودع الكود.

## 20.5 بنية الصيانة والتحديث للمشروع التجاري

### تقسيم مبدئي للمستودع

```text
smart-accountant/
  apps/                 # خادم، خدمة فرع، أدوات إدارة، حاوية مكتبية اختيارية
  crates/
    domain/             # أنواع وقواعد المجال المالي الأساسية
    application/        # حالات الاستخدام والموافقات والتنسيق
    infrastructure/     # PostgreSQL، مخزن، رسائل، تكاملات قابلة للاستبدال
    web/                # توجيه وقوالب Askama وجلسات آمنة
    contracts/          # عقود API/الأحداث/الأدوات وإصداراتها
    identity/           # مصادقة وصلاحيات وتدقيق الدعم
    licensing/          # تحقق الترخيص؛ لا مفاتيح خاصة في المنتج
    sync/               # أوامر الفروع وتسوية التعارض
    social/             # نطاق التجارة الاجتماعية
    social-connectors/  # موصل مستقل لكل منصة
    ai/                 # سياسات السياق والأدوات وموصلات المزود
  templates/            # مكونات Askama قابلة لإعادة الاستخدام
  assets/               # CSS، صور، JS محدود ومراجع
  migrations/           # ترحيل قاعدة البيانات بإصدار
  tests/                # خصائص، تكامل، قبول، أمن، محاكاة انقطاع
  docs/                 # قرارات هندسية، سياسات، تشغيل ومقارنات
  tools/                # مولدات، فحوصات، أدوات إصدار واستعادة
```

الأسماء والتقسيم نهائيًا يخضعان لتجربة العمل الفعلي؛ لا يستلزم كل مجلد crate مستقلًا إذا لم تضف الحدود قيمة. قاعدة التبعيات: المجال لا يعتمد على HTTP أو مزود الذكاء أو قاعدة البيانات؛ تتجه الموصلات إلى العقود الأساسية. سجل قرارات هندسية ADR يشرح كل تغيير كبير وتأثيره ومبرراته.

### مسار إصدار آمن

تثبيت نسخ مستقرة متوافقة وفحص مصدرها وصيانتها، lockfile وSBOM، فحص رخص وثغرات وحزمة برمجيات موقعة، `fmt` و`clippy` والاختبارات وفحوص توافق العقود وواجهات القنوات والهجرات. بيئات تطوير وتجربة وإنتاج منفصلة، إصدار تجريبي ثم إطلاق تدريجي ومراقبة وتراجع بخطة واضحة بعد نسخة احتياطية. يصدر تحذير لدعم الإصدارات المنتهية من APIs الخارجية، مع اختبارات توافق وحلول استبدال قبل إيقاف الإصدار. لا يعمل تحديث تلقائي على بيانات الإنتاج دون سياسة وحق صريح للعميل وخطة استرداد؛ لا يضمن الإرجاع الآلي سلامة كل هجرة.

## 20.6 التعديلات على بوابات مراحل التنفيذ

- **مرحلة الاكتشاف:** مصفوفة منافسين مفصلة، مقابلات منشآت يمنية، مواصفات باقات النظام، إجراءات حقوق الملكية والدعم واشتراطات قنوات Meta، ومتطلبات العتاد والاتصال.
- **مرحلة الأساس:** بنية التراخيص الموقعة ونموذج المورد/العميل وعزل الشركات والاسترداد، مع المحاسبة الأساسية. لا يوصف الترخيص أو الاسترداد بأنه آمن قبل اختبارات مستقلة.
- **المبيعات:** نموذج طلب موحد، ثم موصل WhatsApp/Messenger ومعالج الإعداد والبوابة العامة بعد إتاحة حسابات واختبارات وتفويض حقيقي، لا مجرد حقول إعداد شكلية.
- **المساعد:** سياق قابل للتحكم وملء شفاف؛ كل إجراء يمر بسياسة الموافقة. اختبارات الخصوصية واللهجة جزء من شرط القبول.
- **الإطلاق التجاري:** مراجعة أمن وتراخيص ومحاسبة وضرائب، اختبار دعم واسترداد لمالك حساب فقد جميع بيانات الدخول، اختبار تحويل/انتهاء ترخيص وحماية بيانات العميل، فحص جاهزية القنوات وشروط Meta لكل بلد. مقارنة موثقة بالمنتج/الإصدار المستهدف، لا مقارنة تسويقية غير مثبتة.

# 21. ملحق تجربة الاستخدام والتنقل والصيانة المحلية

**الحالة:** متطلبات تصميم معتمدة من صاحب المشروع، لم تُنفذ أو تُختبر بعد. عند اختلاف أي نص سابق عن توضيحات هذا القسم، يعتمد هذا القسم، وقد عُدلت البنود السابقة الرئيسية لتجنب التعارض.

## 21.1 حرية كلمة المرور وحساب المهندس المحلي

1. **حساب المستخدم:** الاسم بالعربية أو غيرها؛ يختار المستخدم كلمة مرور من محرف واحد أو أكثر، حرفًا أو رقمًا أو غيرهما، دون فرض نوع محارف أو حد أدنى أكبر من واحد، ودون إلزام بعامل ثانٍ. عدم قبول كلمة فارغة مطلب منفصل عن حرية اختيار حرف واحد. يسمح النظام بالكلمات الطويلة دون اقتطاع صامت، ويحدد حدًا تقنيًا معلنًا وعاليًا للمدخلات لمنع إساءة استخدام الموارد.
2. **الحماية:** تحفظ كلمات المرور كتجزئة آمنة بملح مستقل، ولا تخزن كنص مقروء أو في سجلات النظام. توضع ضوابط لتكرار محاولات الدخول من دون تحويلها إلى شرط لطول كلمة المرور. كلمة المرور القصيرة أسهل تخمينًا، حتى على جهاز محلي؛ هذه ملاحظة عن المخاطر وليست مانعًا لاختيارها.
3. **حساب المهندس:** نافذة محلية خاصة بإعدادات المهندس وصيانة المنتج والتراخيص والتشخيص. يسجل المهندس الدخول بكلمة خاصة به، ويفتح حسابات وشاشات الشركة على الجهاز المحلي لأغراض الصيانة، وفق الصلاحية المهيأة له، دون اعتماد خدمة وصول عن بُعد ودون طلب موافقة جديدة على كل نافذة. يمكنه استعادة اسم الحساب وإعادة تعيين كلمة مروره بعد التحقق من هوية صاحبه؛ لا يمكن إظهار كلمة المرور الأصلية لأنها ليست محفوظة بنصها.
4. **شفافية الصيانة:** تظهر هوية المهندس ووضع الصيانة وتُسجل الإجراءات الحساسة دون تسجيل كلمة السر. فتح حساب العميل أو نافذة لا يشكل موافقة على ترحيل قيود أو دفع أموال؛ تُطبق دورة الاعتماد المالي المحددة. يُفضل إنشاء كلمة مهندس مستقلة وقابلة للتغيير لكل تثبيت؛ الوصول المحلي يحد من التعرض عبر الشبكة لكنه لا يلغي مخاطر تسرب الكلمة أو استعمال الجهاز.
5. يُفصل حساب المهندس المحلي عن مفاتيح توقيع التراخيص وخدمة إدارتها؛ لا يُشحن مفتاح التوقيع الخاص داخل برنامج العميل. هذا الفصل لا يمنع صيانة النسخة دون اتصال.

## 21.2 الشرح السياقي الموحد لكل عنصر

**المطلب:** عند التأشير بالمؤشر على أي حقل أو نافذة أو عمود أو صف أو تبويب أو زر أو بطاقة، يعرض النظام شرحًا عربيًا مختصرًا خاصًا بالعنصر وبحالة استخدامه. يُستخدم معرّف ثابت لكل عنصر في عقد الواجهة، ويخضع الشرح للترجمة والإصدار والصلاحيات.

| العنصر | محتوى الشرح | مثال |
|---|---|---|
| نافذة أو بطاقة إدارة | الغرض ومحتوى الشاشة أو الإدارة | «المشتريات: إدارة الموردين وطلبات الشراء والفواتير والمدفوعات.» |
| حقل إدخال | ما يجب إدخاله، والصيغة أو الوحدة، والإلزام إن وجد | «سعر الصرف: أدخل قيمة وحدة واحدة من عملة المستند بالعملة الوظيفية.» |
| تبويب | البيانات والإجراءات المتاحة داخله | «القيود: استعراض مسودات القيود وقيود الفترة المرحّلة.» |
| رأس عمود | معنى القيمة ووحدتها وكيفية حسابها بإيجاز | «الرصيد: الفرق بين الحركات المدينة والدائنة وفق طبيعة الحساب.» |
| صف بيانات | تعريف الصف وحالته والإجراء المتاح بحسب الصلاحية | «فاتورة شراء: مسودة، لا تؤثر في الحسابات حتى الترحيل.» |
| زر أو إجراء | النتيجة المتوقعة وأثرها المهم | «معاينة: اعرض الأثر المحاسبي قبل طلب الاعتماد.» |

**السلوك:**
- إظهار التلميح عند تحريك الماوس أو التركيز بلوحة المفاتيح، مع إتاحته عبر لمس/زر مساعدة على الشاشات اللمسية. لا يعتمد المستخدم على الماوس وحده، وتبقى التعليمات الأساسية ظاهرة قرب الحقل عند الحاجة.
- تأخير ظهور بسيط قابل للضبط لمنع الوميض أثناء التنقل السريع؛ يستمر الشرح ما دام المؤشر أو التركيز داخل العنصر أو محتوى الشرح، ويغلق بـ Escape أو عند الانتقال. توضع النافذة بحيث لا تحجب الإدخال أو المعلومات المهمة قدر الإمكان [U1].
- الشرح النصي غير التفاعلي يستخدم مكون tooltip وربطًا مناسبًا لقارئات الشاشة. إن احتوى روابط أو أزرارًا يستخدم مكون popover/dialog مناسبًا بدل حشر عناصر تفاعلية داخل tooltip [U2].
- عند تداخل صف وخلية وعمود، أولوية الشرح لأدق عنصر تحت المؤشر؛ يُتاح شرح الصف من عنوانه أو منطقة مخصصة وشرح العمود من رأسه، دون إظهار ثلاث نوافذ فوق بعضها. تُحمّل شروح الصفوف ديناميكيًا من بيانات مصرح بها وبما يلائم الجداول الكبيرة دون إنشاء آلاف نوافذ مستقلة.
- الشرح يوضح الإلزام والوحدة والآثار بحسب السياق، ولا يعرض أرقام العملاء أو معلومات محجوبة. إذا كانت المعلومة غير متاحة يظهر وصف عام صحيح، مع تسجيل نقص الوصف في فحص جودة التطوير؛ لا يُختلق شرح.
- يدير المستخدم حجم النص، وزمن الإظهار، وكثافة الشرح، ووضع المساعدة؛ افتراضيًا تكون الشروح مفعلة. للمطور أو المختبر تقرير يغطي العناصر التي تفتقر لشروح، ويمنع إصدار الشاشة قبل اكتمال التعريفات المطلوبة.

**عقد بيانات المساعدة:** `element_id، نوع_العنصر، label، short_help، detailed_help اختياري، قواعد_الحقل، الحالة، اللغة، الصلاحية، الإصدار`. يشارك هذا العقد في قوالب Askama والنماذج والجداول والمساعدة والاختبارات، مع مراجعة بشرية للمحتوى المحاسبي. لا ينشئ الذكاء الاصطناعي قواعد إلزامية من تلقاء نفسه.

## 21.3 التوسعات والتفرعات والارتباطات

المقصود هو بناء نظام هرمي وترابطي **قابل للتوسع** يغطي لكل إدارة وشاشة وبياناتها وعلاقاتها وعملياتها ما يُعتمد في تحليل المجال، وليس الادعاء بأن جميع تفاصيل كل نشاط قد عُرفت مسبقًا.

- **الهيكل:** منتج ← شركات ← فروع ← إدارات ← أقسام ← شاشات/تبويبات ← مكونات وحقول ← إجراءات ونتائج. لكل مستوى معرف دائم واسم ووصف وصلاحية وحالة ونسخة ومسار.
- **علاقات المجال:** يعرّف عقد كل كيان ارتباطاته، مثل المستند ← العميل/المورد ← الأصناف/المخزن ← الضريبة/العملة ← التسعير ← الاعتماد ← القيد ← التحصيل/الدفع ← التقرير/الإيصال. يدعم النظام تتبع المرجع والانتقال المباشر بين العناصر وفق الصلاحيات.
- **اعتماد الحقول:** يحدد العقد نوع الحقل ومدخله وقيمته الافتراضية ومصدره وما يعتمد عليه، وظهوره وإلزامه، والتحقق، والإجراءات التي يعيد احتسابها، والوحدة والدقة. إذا تغير حقل مؤثر تظهر التغييرات التابعة وتعاد مراجعة القيم والاعتماد عند اللزوم؛ لا يُغير مبلغ أو حساب أو سعر بصمت.
- **اعتماد العمليات:** مخططات حالة وإجراءات صريحة تحدد ما يسمح قبل العملية وبعدها، وآثارها على المحاسبة والمخزون والعملاء والصلاحيات، وما يمكن عكسه. يرفض النظام العلاقات الدائرية أو غير المكتملة عندما تؤدي إلى نتائج غير آمنة ويظهر الخطأ للمطور/المخول.
- **إمكانية الإضافة:** سجل إدارة موحد لتعريف الهيكل والتنقل والمساعدة والصلاحيات؛ يُولد منه ما يمكن توليده من عرض واختبارات، مع ضرورة كتابة منطق الأعمال الجديد واختباره ومراجعته. لا يترتب على إضافة بطاقة وحدها وجود إدارة أو امتثال محاسبي جاهز.

**مثال تتبع:** من فاتورة بيع مرّحلة، يرى المخوّل العميل والأصناف والتسليم والتحصيل والقيد وإيصال القيد الثلاثي عند توفره، ثم يعود إلى الفاتورة دون فقد موضعه. إذا لم يكن إيصال الطرف الآخر مكتملًا تظهر حالته الفعلية بدل اعتباره مثبتًا.

## 21.4 شريط الاختصارات والتنقل

- شريط قابل للتخصيص يضيف إليه كل مستخدم الشاشات والتبويبات والتقارير والإجراءات المخوّل بها؛ يدعم التثبيت والإزالة وإعادة الترتيب والتصنيف والأيقونات والبحث، مع فتح الشاشة أو الإجراء الصحيح لا نسخة مكررة بلا داعٍ.
- حفظ الاختصارات باسم المستخدم والشركة، مع اختيار ما إذا كانت مشتركة بين فروع الشركة أو خاصة بفرع، ومزامنتها بين أجهزته إن فعّل ذلك. إذا ألغيت صلاحية المستخدم أو أُزيلت شاشة، لا يعمل الاختصار ويُعرض السبب المناسب دون كشف أسماء أو بيانات محظورة.
- وسائل وصول إضافية: بحث شامل مصرح به، مسار تنقل، قائمة آخر الشاشات، قائمة العناصر ذات الصلة، اختصارات لوحة مفاتيح قابلة للتعديل أو الإيقاف، وأوامر المساعد التي تفتح شاشة محددة دون تجاوز الصلاحيات. تمنع التعارضات مع اختصارات المتصفح ولوحة المفاتيح وأدوات الوصول قدر الإمكان.
- نافذة منبثقة سريعة لمهام مثل البحث عن عميل أو معاينة مستند أو اختيار حساب؛ النماذج المعقدة تُفتح كشاشة أو مساحة كاملة عندما يتطلب العمل ذلك. الإغلاق يعيد التركيز لموضعه، ولا يمسح بيانات غير محفوظة دون تنبيه.

## 21.5 تعدد النوافذ ومساحة العمل

**متطلب:** فتح نافذة أو شاشة جديدة إلى جانب الحالية، مع الاستمرار في العمل على كلتيهما دون فقد السياق. يدعم التصميم ثلاثة أنماط:

1. **تبويبات داخل التطبيق:** فتح شاشات متعددة، التنقل بينها وإغلاقها وتثبيتها وإظهار حالة المسودة.
2. **عرض متجاور/مقسم:** وضع نافذتين أو أكثر داخل مساحة العمل، وتغيير الأحجام أو ترتيبها أو تكبير إحداها، وفق قيود الجهاز وإمكانية الوصول. في الشاشات الصغيرة تتحول بسلاسة إلى تبويبات أو عرض عمودي.
3. **نافذة مستقلة عند الدعم:** فتح عرض في نافذة متصفح أو حاوية سطح المكتب إذا سمحت بيئة التشغيل وسياسة الجهاز؛ إن حُجبت النوافذ المنبثقة، يعرض النظام السبب ويتيح فتحها داخل التطبيق. لا يفترض هذا توفر Tauri أو إمكانية فتح نافذة نظام مستقلة على كل منصة.

**سلامة البيانات عند تعدد النوافذ:**
- لكل نافذة سياق واضح: الشركة والفرع والمستند والعملة وحالة الصلاحية. لا يتغير سياق نافذة أخرى بصمت عند تغيير الشركة في نافذة واحدة؛ يُسأل المستخدم عند الحاجة لتوحيد السياق.
- تخزين مسودات صريح أو حفظ تلقائي مضبوط مع مؤشر الحالة. لا يُسترجع سر أو مسودة حساسة لشخص آخر على جهاز مشترك؛ تتبع الاستعادة صلاحيات وسياسة الجلسة.
- عند فتح المستند نفسه في نافذتين، يُستخدم رقم إصدار والتحقق عند الحفظ؛ لا يطغى تعديل على آخر بصمت. يعرض النظام تعارض النسخ وخيارات مراجعة/تحديث/حفظ مسودة بحسب نوع المستند والصلاحية.
- بعد أي تعديل مؤثر يفقد اعتماد المعاينة السابقة صلاحيته؛ يمنع مفتاح عدم التكرار تكرار القيد أو الدفع إذا نُفذ الإجراء من نافذتين. تحديث الصلاحيات وحالة الترحيل يصل للنوافذ المفتوحة أو يعاد التحقق عند أي إجراء.
- عند إغلاق نافذة تحوي تغييرات غير محفوظة يظهر خيار الحفظ أو الإلغاء أو البقاء؛ وعند انقطاع الاتصال تُعرض حالة الحفظ المحلي والمزامنة وفق سياسة الفرع. تُراعى العناوين وموضع التركيز وإغلاق النافذة المنبثقة بلوحة المفاتيح.

## 21.6 معايير القبول للمتطلبات الجديدة

1. إنشاء حساب عربي بكلمة `1`، وآخر بكلمة `أ`، وتسجيل الدخول دون إلزام بعامل ثانٍ أو أنواع محارف؛ وتخزينهما بتجزئة آمنة وعدم ظهورهما في السجلات. تُختبر أيضًا كلمة طويلة وعدم اقتطاعها.
2. دخول المهندس محليًا وفتح حساب وشاشة للصيانة دون شبكة أو مطالبة بموافقة جديدة لكل نافذة، مع ظهور وضع المهندس وتسجيل عملياته؛ إعادة تعيين كلمة مرور منسية دون استرجاع النص الأصلي.
3. اختبار الشرح لكل نوع عنصر بالماوس ولوحة المفاتيح واللمس وقارئ الشاشة؛ ظهور وصف الحقل والعمود والصف الصحيح، وإغلاقه بـ Escape، وعدم الحجب أو الوميض، وعدم ظهور بيانات غير مصرح بها.
4. إضافة شاشة وتبويب للاختصارات، تغيير ترتيبهما، تسجيل الخروج والدخول، اختبار تغير الفرع وإزالة الصلاحية. ينبغي أن يفتح الاختصار الوجهة المصرح بها فقط.
5. فتح فاتورة وعميل جنبًا إلى جنب، ثم فتح المستند نفسه في نافذتين وتعديلهما؛ ظهور التعارض بدل الكتابة الصامتة، ومنع تكرار الترحيل، وإبطال الموافقة عند تغير البيانات.
6. اختبار النوافذ المنبثقة المحجوبة، تبديل السياق، الشاشة الصغيرة، المسودة غير المحفوظة وانقطاع الشبكة. توثيق نتيجة كل اختبار وحالات الفشل المتبقية قبل الإصدار.
