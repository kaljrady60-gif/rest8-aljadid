# خطة بناء قسم المبيعات

مرجع الجرد: `docs/جرد_المرجع_المبيعات.md`. هذه الخطة قابلة للتنفيذ مرحلةً مرحلة، وكل مرحلة تنتهي بشرط قبول قابل للقياس **واختبارات فعلية**، لا بـ«يعمل».

**قواعد ثابتة تحكم كل مرحلة**

| القاعدة | التطبيق |
|---|---|
| ملف ≤ 700 سطر | كل ملف جديد تحت 400 سطر افتراضيًا؛ التجاوز مرفوض في المراجعة |
| لا بناء جانبي | لا صفحة مستقلة، لا HTML مبعثر — كل شيء داخل شاشات قسم المبيعات |
| عربي RTL | كل النصوص والعناوين، والتواريخ LTR |
| لا ألوان كحلي/داكن | تُستخدم رموز `15-actions.css` الحالية |
| ترتيب الشاشة | قسم اليومية/المستند أولًا، التقرير/الجدول أدناه |
| الحالة | تُعرض كشارة نصية عربية؛ لا «مسودة» مجرّدة بلا لون دلالي |
| الترحيل | نمرّ عبر محرّك القيود القائم؛ لا قيد خارج المسار |
| البرهان | كل مرحلة تُثبت بلقطات في `reports/shots/` + مخرجات API |

## المرحلة 1 — الأساس والمخطط (Sales Foundation)

**الملفات**

| ملف | المحتوى | تقدير |
|---|---|---|
| `src/sales/mod.rs` | `pub mod` + `router()` تلصق على `AppState` | 120 |
| `src/sales/schema.rs` | 14 جدولًا أساسيًا + فهارس + قيود | 300 |
| `src/sales/scope.rs` | عزل الشركة/الفرع (نسخة من `finance::scope` بمعرّف نطاق مبيعات) | 140 |
| `src/sales/numbering.rs` | بادئات INV/QT/OR/RT/POS وربطها بوحدة `finance::numbering` | 90 |

**المخطط (مبسّط تصميمًا، غنيّ بالقيود)**

```
sales_customer_groups(id, company_id, branch_id, code, name, discount_bp, status)
sales_reps(id, company_id, branch_id, number, name, phone, commission_bp, status)
sales_collectors(id, ..., number, name, phone, commission_bp, status)
sales_credit_cards(id, ..., name, network_limit_minor, off_network_limit_minor, commission_bp, status)
sales_types(id, ..., code, name, kind, category, status)
sales_return_reasons(id, ..., code, name, category, status)
sales_invoices(id, ..., number, invoice_type, invoice_date, party_id, currency, description,
               status, journal_entry_id, original_invoice_id, warehouse_id,
               total_minor, discount_minor, tax_minor, net_minor, pos_machine_id, pos_cashier,
               created_by, created_at, UNIQUE(company_id, number))
sales_invoice_lines(id, ..., invoice_id, item_id, description, qty, price_minor, discount_minor, tax_bp, net_minor,
               CHECK(qty > 0), CHECK(price_minor >= 0))
sales_orders(...) / sales_order_lines(... discounted_qty)
sales_quotations(...) / sales_quotation_lines(...)
```

- كل مبلغ `_minor` (صحيح)، كل نسبة `_bp`.
- كل مفاتيح الربط بـ`REFERENCES … ON DELETE RESTRICT` (خلافًا للمرجع) — ونُثبت ذلك باختبار يحاول الحذف فيُرفض.
- `sales_invoices.party_id` يشير إلى `finance_parties` (الدور `customer`) — **إعادة استخدام، لا جدول عملاء جديد**.
- إبقاء `global_id` و`origin_branch_id` أعمدةً فارغة لتفادي هجرة المزامنة لاحقًا.

**نقاط النهاية**

- `GET /api/sales/setup` — كل الكيانات المساندة في نداء واحد (شاشة التهيئة).
- `POST /api/sales/{entity}` — إنشاء/تعديل عامّ محكوم بقائمة بيضاء للحقول.
- `GET /api/sales/invoices?status=&type=&party=` — قائمة بترقيم.

**شرط القبول**
1. `GET /api/sales/setup` يعيد 200 بكل المصفوفات فارغة في قاعدة جديدة.
2. محاولة إدراج سطر بكمية 0 تُرفض برسالة عربية واضحة.
3. حذف عميل مرتبط بفاتورة يُرفض (اختبار وحدة).

**اختبارات:** 6 اختبارات وحدة على القيود + اختبار عزل شركة (شركة 2 لا ترى فواتير شركة 1).

## المرحلة 2 — فاتورة البيع والمرتجع (نواة القسم)

**الملفات:** `src/sales/invoices.rs` (350)، `src/sales/invoice_post.rs` (200)، `src/sales/returns.rs` (180).

**المنطق**
1. إنشاء مسودة: سطور + خصم + ضريبة ← حساب `net_minor` من الخادم (لا من المتصفح).
2. `POST /api/sales/invoices/{id}/post`:
   - تحقق: سطور ≥ 1، عميل نشط، سعر > 0.
   - استدعاء محرّك القيود: مدين `العملاء` / دائن `الإيرادات` (+ ضريبة `ضريبة المخرجات`).
   - البيان عبر `finance::narrative::compose("بيع", number, party_name)`.
   - الحالة ← `posted` + `journal_entry_id`؛ بعدها **المنع المطلق** للتعديل.
3. المرتجع: ينشأ من فاتورة مرحّلة فقط، `original_invoice_id` إلزامي، الكميات ≤ كميات الأصل، والأسعار مقفلة من الأصل.
   - القيد عكسي: مدين `الإيرادات` / دائن `العملاء`.

**نقاط النهاية:** `POST /api/sales/invoices`, `POST /api/sales/invoices/{id}/post`, `POST /api/sales/invoices/{id}/cancel`, `POST /api/sales/returns`.

**شرط القبول**
1. ترحيل فاتورة 1,000 + ضريبة 15% ⇒ قيد بسطرين/ثلاثة متوازنة، والخادم يعيد `journal_entry_id`.
2. محاولة تعديل مسودة مرحّلة ⇒ 409 برسالة «القيود المرحّلة غير قابلة للتعديل».
3. مرتجع بكمية أكبر من الأصل ⇒ 422.
4. بيان القيد الناتج يطابق `بيع INV-2026-0001 — اسم العميل`.

## المرحلة 3 — الأصناف والعروض والطلبات

**الملفات:** `src/sales/catalog_link.rs` (120)، `src/sales/orders.rs` (260)، `src/sales/quotes.rs` (240).

- أصناف: جسر إلى المخزون. إلى أن يكتمل قسم المخزون، جدول `sales_item_refs(id, company_id, code, name, unit, price_minor, tax_bp, active)` — يُستبدل لاحقًا بعلاقة مباشرة، مع إبقاء نفس الواجهة.
- عرض سعر: `valid_until`، حالة `sent/accepted/expired`.
- تحويل: عرض ← فاتورة (`converted_invoice_id`)، طلب ← فاتورة (`invoice_id`)، كل تحويل ذرّي داخل معاملة واحدة.
- طلب العميل: `delivered_qty` لكل سطر، ومنه ينشأ «تسليم جزئي» يقلّل الكمية القابلة للفوترة.
- الخصم: `discount_bp` من مجموعة العميل يُقترح تلقائيًا، ويمكن تجاوزه يدويًا (مع تسجيل من تجاوز).

**شرط القبول**
1. تحويل عرض 3 سطور ⇒ فاتورة 3 سطور بنفس المبالغ، وبعدد نقرات 1.
2. طلب بـ`delivered_qty` أقل من الكمية ⇒ فاتورة جزئية، والرصيد يبقى قابلاً للفوترة.
3. عرض منتهي (`valid_until` < اليوم) لا يُحوّل ⇒ 422.

## المرحلة 5 — العمولات والتقارير

**الملفات:** `src/sales/commissions.rs` (220)، `src/sales/reports.rs` (300).

- خطط/قواعد/احتساب: `commission_calcs` بدورة شهرية، الأساس صريح (بيع/تحصيل).
- «ترحيل استحقاق العمولة»: زر يولّد قيدًا مدينًا `مصروف عمولات` / دائنًا `عمولات مستحقة` عبر نفس المحرّك.
- تقرير الأعمار: 0–30/31–60/61–90/90+ لكل عميل ومجموعة، مع مفتاح تاريخي (تاريخ الفاتورة أو الاستحقاق).
- تقرير تحليلي: بالصنف/المندوب/المجموعة/الشهر، مع تصدير CSV (نفس وحدة التصدير المالية).

**شرط القبول:** مجموع الأعمار = إجمالي الذمم المدينة في الميزان (فرق = 0.00)، ويُثبت باختبار على بيانات العرض.

## المرحلة 6 — POS والولاء

- فتح وردية: ماكينة + كاشير + عهدة ابتدائية.
- بيع POS: فاتورة `posted` تلقائيًا + خصم من المخزن (عند توفّره) + نقاط ولاء.
- إقفال وردية: نقد متوقع = عهدة ابتدائية + مبيعات نقدية − مرتجعات؛ يُقارن بالمسلَّم ويُسجَّل الفرق.
- نقاط الولاء: `spend_per_point_minor` و`point_value_minor`؛ الصرف يولّد خصمًا بحد أقصى.

**شرط القبول:** إقفال وردية بفرق نقدي 0 ينتج تقريرًا مطابقًا؛ وفرق 5 يُبرز بالأحمر الدلالي في نفس الصفحة.

## المرحلة 7 — التماسك والتشطيب

1. تطبيق `18-action-semantics.js` على كل أزرار المبيعات (يعمل تلقائيًا — يحتاج تحققًا بصريًا فقط).
2. توحيد البيان في كل مستندات المبيعات عبر `narrative`.
3. `seed` لمبيعات تجريبية كاملة: 12 فاتورة، 3 مرتجعات، عرضان، طلبان، عمولتان.
4. اختبار قبول شامل آلي (Playwright): فتح القسم ← إنشاء فاتورة ← ترحيل ← تحقق ظهورها في القيود اليومية بدفتر المالية.
5. تقرير `reports/تقرير_المبيعات_100.md` بنفس نمط تقرير المالية.
